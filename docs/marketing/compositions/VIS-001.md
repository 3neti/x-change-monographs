# VIS-001 — Core Pay Code Journey

## Record

- **Class:** Primary composition
- **Status:** Canonical concept
- **Question answered:** How can I send without knowing where the recipient banks or which provider they use?
- **Core insight:** Generate a Pay Code, share it, and let the recipient claim through one available supported destination.

## Composition

```text
Generate              Share                 Claim
   ↓                    ↓                      ↓
ILL-002 ───────────→ ILL-003 ───────────→ ILL-004
                                                └── ILL-005
                                                    choice inside Claim
```

## Source illustrations

- ILL-002 — Generate Pay Code
- ILL-003 — Share Pay Code

- ILL-005 — Recipient Choice, nested within ILL-004

## Semantic icon dependencies

ICN-001 Person, ICN-002 Institution, ICN-003 Pay Code, ICN-004 Instruction, ICN-009 Choice, ICN-010 Journey, ICN-011 Destination, ICN-013 Communication, ICN-008 Validation, ICN-014 Settlement, and ICN-015 Completion.

## Reading order

1. An intended payment becomes a Pay Code within a governed context.
2. The same Pay Code moves through one ordinary communication path.
3. Movement stops with the recipient.
4. Supported choices become visible inside Claim.
5. One destination is selected and one completion follows.

## Primary hierarchy

1. The three verbs: Generate, Share, Claim.
2. One continuous credential journey.
3. Human agency within Claim.
4. Quiet institutional responsibility and validation.

## Nested complexity

Authorization remains inside Generate. Choice, presentation, validation, settlement, completion, and evidence remain inside Claim. None becomes a fourth first-level step.

## Canonical remembered sketch

```text
Generate → Share → Claim
                     └ choice
```

If a viewer remembers more steps than this, the adaptation is too complicated. If choice appears beside Claim, the hierarchy is wrong.

## Permitted adaptations

- Horizontal or vertical arrangement.
- Progressive reveal or static presentation.
- Removal of secondary institutional detail at small scale.
- Enlargement of Claim using VIS-006 without altering the first-level sequence.
- Translation of labels using governed wording.

## Prohibited mutations

- Adding Authorize, Choose, Validate, Receive, or Settle as a peer step.
- Changing the order of the three verbs.
- Showing money moving through the Pay Code or communication channel.
- Splitting one Pay Code into several claims or completions.
- Presenting unlimited destinations.
- Making a platform, QR, institution, or credential the hero.

## Accessibility summary

A responsible institution generates a Pay Code for an intended payment. The sender shares the same credential with the intended recipient. During Claim, the recipient presents it, chooses one available supported destination, and completes the governed journey after applicable validation.

## Validation profile

Required:

- Fifteen-Second Test
- Caption Test
- Doctrine Test
- Memory Test

VIS-001 passes only when a first-time viewer can reproduce the canonical remembered sketch after one exposure.
