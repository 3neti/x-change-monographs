# VIS-005 — Problem Before Solution

## Record

- **Class:** Primary composition
- **Status:** Canonical concept
- **Question answered:** Why should the sender need a Pay Code?
- **Core insight:** The sender knows the intended recipient but should not need to know that person's bank, wallet, or provider details upfront.

## Composition

```text
ILL-001 Unknown Recipient Destination
                 ↓
VIS-001 Core Pay Code Journey
```

## Source dependencies

- ILL-001 — Unknown Recipient Destination
- VIS-001 — Core Pay Code Journey

## Semantic icon dependencies

ICN-001 Person, ICN-002 Institution, ICN-003 Pay Code, ICN-009 Choice, ICN-010 Journey, and ICN-011 Destination.

## Reading order

1. The sender and recipient are known to one another.
2. Only the recipient's destination is unknown.
3. VIS-001 resolves the problem through Generate, Share, and Claim.

## Primary hierarchy

1. Human relationship.
2. Unknown destination.
3. Simple Pay Code journey.

## Nested complexity

Identity and applicable controls still exist. The visual uncertainty belongs only to the destination and must not transfer to the recipient.

## Permitted adaptations

- Use ILL-001 as an opening frame followed by VIS-001.
- Place the problem and solution side by side when the reading order remains obvious.
- Compress ILL-001 into a headline-supported cue for brief surfaces.

## Prohibited mutations

- A question mark over the recipient.
- Implying anonymous or unverified payment.
- Presenting unknown destination as unlimited acceptance.
- Adding a technical integration problem before the human problem.

## Accessibility summary

A sender knows the intended recipient but does not know which bank, wallet, or provider the person uses. The Pay Code journey lets the sender generate and share a credential so the recipient can claim through one available supported destination.

## Validation profile

Required: Fifteen-Second Test, Caption Test, Doctrine Test, and Memory Test. The remembered solution must remain Generate → Share → Claim.
