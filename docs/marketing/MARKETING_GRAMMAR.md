# Marketing Grammar

## Purpose

The Marketing Grammar provides reusable message blocks for introducing Pay Code quickly and consistently. Publications select from these blocks; they do not improvise a new product definition for each format.

## Core terms

### Pay Code

A portable credential representing an authorized financial instruction. It may be communicated and presented through a supported journey. It is not money, a deposit, stored value, a wallet balance, or the financial service itself.

### Authorized Instruction

The governed direction behind a Pay Code: who has authorized an outcome, for what purpose or amount, for whom, and subject to which conditions.

### Supported Journey

An approved way to communicate, present, validate, and complete the instruction through participating institutions, providers, and channels.

### Recipient Choice

The recipient's ability to use an available supported destination without requiring the sender to know that destination in advance. Recipient Choice never means universal acceptance or the absence of identity, policy, eligibility, or compliance requirements.

## Canonical message blocks

### MSG-001 — One-sentence definition

> Send a Pay Code. The recipient chooses where to receive.

### MSG-002 — Supporting line

> No bank account, e-wallet, or provider details needed upfront.

### MSG-003 — 30-second explanation

> Generate a Pay Code. Share it. The recipient claims it through a supported channel and chooses where to receive.

### MSG-004 — Three-step explanation

1. **Generate** — Create a Pay Code for the payment.
2. **Share** — Send it to the recipient.
3. **Claim** — The recipient presents it and chooses an available way to receive.

### MSG-005 — Elevator pitch

> A Pay Code gives a payment instruction a portable credential. The sender shares the code. The recipient claims it through a supported channel—without the sender needing their account or provider details upfront.

### MSG-006 — Doctrine anchor

> Money should adapt to people. Not the other way around.

### MSG-007 — Service distinction

> The financial service is the product. The Pay Code is the credential.

### MSG-008 — Boundary statement

> A Pay Code does not hold money and is not a deposit, wallet balance, stored value, or promise of universal acceptance. Completion remains subject to the responsible institution, supported channels, participating providers, and applicable conditions.

| ID | Call to action | Intended destination |
| --- | --- | --- |
| CTA-001 | See how a Pay Code works. | Demonstration or explainer |
| CTA-002 | Explore an institutional use case. | Relevant Program Guide |
| CTA-003 | Bring one payment or disbursement workflow. | Discovery conversation |
| CTA-004 | Discuss a controlled demonstration. | Demonstration planning |
| CTA-005 | Read the operating model. | Executive Reading Note or Program Guide |

Calls to action invite observation and examination. They must not presume adoption, approval, licensing, procurement, implementation, or production readiness.

## Representative-use language

Approved universal examples include payroll, government benefits, insurance claims, merchant refunds, remittance, emergency assistance, loan proceeds, and incentives. These are possible applications of the operating grammar, not claims of current deployment, provider availability, or regulatory approval.

## Compression rule

When space is constrained, preserve content in this order:

1. `MSG-001` primary message;
2. `MSG-002` supporting line;
3. the Generate → Share → Claim visual sequence;
4. one call to action; and
5. the credential boundary in metadata or restrained supporting copy.

Never remove the distinction between credential and money merely to make a layout shorter.
